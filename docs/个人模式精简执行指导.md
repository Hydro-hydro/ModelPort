# 个人使用模式精简执行指导

> 文档日期：2026-09-01
> 最近更新：2026-09-02
>
> 本文用于源码盘点、执行规划和当前改造进度；协议转换核心暂不修改。

## 1. 目标与边界

ModelPort 的目标是保留一个个人用户真正需要的“大模型渠道聚合与协议转换网关”，而不是继续维护完整的多用户运营平台。

个人模式的目标状态：

- 一个管理员账号负责全部管理工作；
- 多个上游渠道、模型和 API Key 聚合到统一入口；
- 保留渠道选择、优先级/权重、失败重试、模型映射和协议转换；
- 保留必要的令牌鉴权、日志、用量统计和调试能力；
- 默认不启用注册、充值、支付、订阅、邀请、兑换码等平台运营能力；
- 默认不启用组织、团队、普通用户、复杂权限和多租户隔离；
- 通过“禁用/隐藏/解耦/删除”四个层次逐步精简，而不是一次性物理删除。

这里的“个人使用”是部署和授权范围，不是把安全校验、额度保护、审计日志或上游协议能力全部关闭。个人模式仍然需要防止错误的请求转换、渠道泄漏、Key 泄漏、无限重试和异常计费。

## 2. 个人模式参数与改造前现状

当前代码中的开关是：

```text
SelfUseModeEnabled
```

对应变量：

```text
setting/operation_setting/operation_setting.go
operation_setting.SelfUseModeEnabled
```

当前完整链路：

```text
首次初始化页面选择 Personal use
  → web/src/features/setup/api.ts
  → POST /api/setup
  → controller.SetupRequest.SelfUseModeEnabled
  → controller.PostSetup
  → model.UpdateOption("SelfUseModeEnabled", ...)
  → model.updateOptionMap()
  → operation_setting.SelfUseModeEnabled
```

在本轮改造前，这个参数实际只影响两个核心行为：

1. **登录页隐藏注册入口**
   - `web/src/features/auth/sign-in/index.tsx`
   - 当 `self_use_mode_enabled=true` 时不显示 Sign up 链接。

2. **允许未配置价格的模型出现在模型列表中**
   - `controller/model.go:ListModels`
   - `setting/ratio_setting/model_ratio.go:GetModelRatio`
   - `relay/helper/price.go:HasModelBillingConfig`
   - 自用模式下，未配置模型倍率/价格的模型可以被视为可用；实际请求仍会经过计费会话和额度逻辑。

在本轮改造前，它**没有**自动完成以下事情：

- 没有关闭注册 API；
- 没有关闭普通用户和多用户数据模型；
- 没有关闭支付、充值、订阅、兑换码；
- 没有关闭 OAuth、邮箱验证、密码找回；
- 没有关闭任务、插件、Midjourney、io.net 部署；
- 没有从后台隐藏无用设置；
- 没有把所有请求固定到唯一管理员或唯一令牌；
- 没有移除用户组、Token 分组、计费分组和渠道分组。

因此，在改造前 `SelfUseModeEnabled` 更接近“自用兼容模式”，不是完整的产品精简模式。

## 2.1 本轮已落地的第一批改造

本轮先实现“能力策略 + 入口收敛”，不删除业务表，也不修改 `relay/`、`relaykit/` 中的协议转换核心：

- `setting/usage_mode/policy.go`：将 `SelfUseModeEnabled` 映射为 `personal` 模式，并集中维护功能能力矩阵；
- `middleware/feature.go`：提供 `RequireFeature`，禁用能力统一返回 `404`、`FEATURE_DISABLED`；
- `/api/status` 和 `/api/capabilities`：向前端提供 `usage_mode` 与 `features`；
- `/api/setup`：继续保留原有配置兼容，同时返回个人模式和演示模式状态；
- 后端路由：注册、密码找回、邮箱验证、OAuth、支付、订阅、兑换码、签到、用户管理、排行榜、任务插件、部署、多节点等入口已增加能力边界；
- 前端导航：个人模式隐藏钱包、用户管理、兑换码、订阅、价格页、排行榜、任务插件、系统信息等入口；
- 前端页面：公开首页 CTA、登录注册入口、个人资料中的签到/OAuth 绑定、仪表盘钱包/价格入口同步按能力隐藏；
- 前端路由：直接访问已隐藏页面时，先按能力跳转，不依赖菜单隐藏；
- 系统设置：OAuth、Passkey、支付、签到、用户组价格、部署、邮件、运营监控等 section 增加能力元数据并按能力过滤；
- 数据库：本轮没有修改 schema、迁移和模型定义，因此暂不触发三数据库迁移矩阵；
- 协议转换：本轮没有修改协议转换核心、Relay 适配器和 `relaykit` 公共 API；
- 计费记账：个人模式的 `NewBillingSession` 已固定使用 `WalletFunding`，不查询或预扣历史订阅；预扣、结算、退款和 Token 额度保护继续复用现有实现；
- 计费测试：新增 `service/personal_billing_test.go`，覆盖个人模式资金来源、结算差额、退款幂等和 Token 额度优先保护。

当前能力策略保留“核心转发能力默认开启、平台运营能力个人模式默认关闭”的原则。未知能力默认视为开启，避免旧代码因未登记能力而被误锁定。个人模式记账仍处于兼容阶段，尚未拆出独立的 `PersonalAccounting` 接口实现。

## 3. 个人模式下的功能分层

### 3.1 必须保留

这些能力直接服务于“聚合多个渠道并统一提供模型 API”：

| 能力 | 主要代码区域 | 原因 |
| --- | --- | --- |
| 渠道 CRUD、Key、Base URL、模型列表 | `model/channel.go`、`controller/channel*.go`、`router/channel-router.go`、`web/src/features/channels` | 配置上游渠道的核心能力 |
| 渠道能力表与路由选择 | `model/ability.go`、`service/channel_select.go`、`service/group.go` | 决定某模型实际走哪个渠道 |
| 优先级、权重、自动分组、失败重试 | `model/ability.go`、`service/channel_select.go`、`middleware/distributor.go` | 多渠道聚合的核心可靠性能力 |
| 模型映射和模型目录 | `model/model_meta.go`、`controller/model*.go`、`web/src/features/models` | 统一外部模型名与不同上游模型名 |
| OpenAI/Anthropic/Gemini/Responses 等 Relay | `router/relay-router.go`、`controller/relay.go`、`relay/`、`relaykit/` | 项目核心目标：协议转换 |
| 请求/响应/流式/工具调用转换 | `relay/`、`relaykit/relayconvert`、`service/request_converter.go` | 修复协议兼容 Bug 的主体 |
| API Token 鉴权 | `model/token.go`、`middleware/auth.go`、`controller/token.go` | 给客户端提供稳定、可撤销的统一入口 |
| 管理员登录和基础账户安全 | `controller/user.go`、`middleware/auth.go`、`model/user*.go` | 保护渠道密钥和系统配置 |
| 请求日志、错误日志、用量记录 | `model/log.go`、`service/log_info_generate.go`、`controller/log.go` | 协议 Bug 定位、渠道质量分析和回归验证 |
| Redis/内存缓存中的必要部分 | `common/redis.go`、`model/*cache.go`、`service/channel_affinity.go` | 额度并发安全、渠道缓存和性能 |
| SQLite 基础部署 | `model/main.go`、数据库初始化代码 | 个人部署应保持低门槛 |
| 必要的健康检查和系统状态 | `controller/misc.go`、`controller/performance.go` | 运行维护和故障诊断 |

### 3.2 保留但收敛

这些功能可能有用，但不应继续以多租户平台的复杂度存在：

| 能力 | 当前问题 | 建议 |
| --- | --- | --- |
| Token | 同时承担用户令牌、分组、额度、模型限制等平台能力 | 个人模式保留多 Token，但默认绑定管理员；保留模型限制和撤销，不强调余额运营 |
| User | 用户模型承载管理员、普通用户、OAuth、钱包、邀请等大量字段 | 短期保留表结构，抽出 `PersonalModePolicy`；UI 默认只展示管理员自身和令牌管理 |
| User Group | 既是权限/价格分组，又参与渠道路由 | 不立即删除；先把“渠道路由组”和“用户计费组”概念拆开，个人模式默认使用单一 `default` 路由组 |
| Quota/Billing | 当前 Relay 生命周期与余额、Token 额度、订阅资金来源交织 | 第一阶段保留安全预扣/结算接口；个人模式使用单一 Wallet/Token 资金策略，隐藏运营计费设置 |
| Pricing | 未配置价格会阻塞模型展示，但协议调试需要模型可用 | 保留最小的“成本/用量记录”模型，不强制个人模式维护销售价和分组价格 |
| 认证 | 账户登录、会话、2FA、Passkey 都有价值，但 OAuth/注册不一定有价值 | 个人模式默认密码登录；2FA/Passkey 可选；注册、OAuth、邮箱找回默认关闭 |
| 日志 | 多用户查询、权限过滤较复杂 | 保留管理员日志、渠道日志、协议转换诊断字段；删除面向普通用户的复杂视图 |
| 系统设置 | 当前按平台运营划分，入口很多 | 个人模式只显示“渠道与协议”“令牌”“日志与诊断”“基础安全”“系统”五类 |

### 3.3 个人模式下默认关闭并从 UI 隐藏

这些功能不应出现在个人模式的默认导航和设置页面中，但第一阶段不建议物理删除后端：

- 普通用户注册和 Sign up 页面；
- 邀请码/推广/分成；
- 钱包充值、提现和充值记录；
- Stripe、Creem、易支付、Waffo、Waffo Pancake 等支付渠道；
- 订阅套餐、订阅购买、订阅重置和订阅支付；
- 兑换码；
- Check-in 签到奖励；
- 邮箱验证和密码重置邮件；
- GitHub、Discord、LinuxDO、微信、Telegram、OIDC 等第三方登录；
- 多用户管理和普通用户权限分配；
- 公开价格页、排行榜、营销首页内容；
- Uptime Kuma、Prometheus/性能指标展示等运营监控页面；
- io.net 模型部署；
- Midjourney、视频、音频、图片等非个人主线能力（是否关闭取决于实际使用）；
- Task Plugin Marketplace 和第三方任务插件管理；
- System Info 中的多节点实例管理；
- 组织/团队/订阅相关的后台菜单。

“隐藏”必须配合后端访问控制，不能只删除侧边栏入口。直接访问 API 路径时，个人模式也应返回明确的 `404` 或“个人模式未启用该功能”，避免形成半可用状态。

### 3.4 评估后可以物理删除或拆为可选模块

以下模块与个人主线耦合相对集中，适合后续拆成可选构建/运行模块：

- `controller/topup*.go` 与对应支付 Provider；
- `controller/subscription*.go`、`model/subscription.go`、`service/subscription_reset_task.go`；
- `controller/redemption.go`、`model/redemption.go`；
- `controller/checkin.go`、`model/checkin.go`；
- `controller/deployment.go`、`pkg/ionet/`、部署相关前端；
- `controller/rankings.go`、`service/rankings.go`、`model/usedata_rankings.go`；
- OAuth Provider 实现及自定义 OAuth 管理；
- 邮箱发送、邮箱验证和忘记密码链路；
- 任务插件 Marketplace 与内置异步任务平台；
- Midjourney 专用 Relay 与任务表；
- ClickHouse 独立日志数据库支持（若个人部署只使用 SQLite）；
- 多节点实例、系统任务锁和跨节点协调（若明确只支持单进程）；
- 运营型数据导出和推广统计。

这些模块不能直接按文件名删除，因为它们被路由、数据库迁移、统一用户模型、计费会话、前端类型和 OpenAPI 文档交叉引用。必须按解耦顺序处理。

## 4. 关键耦合关系

### 4.1 SelfUseModeEnabled 当前耦合图

```text
设置加载
  model/option.go
      ↓
operation_setting.SelfUseModeEnabled
      ├─ controller/model.go: 未配置价格的模型列表策略
      ├─ setting/ratio_setting/model_ratio.go: 未配置倍率时的 success
      ├─ controller/misc.go: /api/status 返回前端标志
      ├─ controller/setup.go: 首次初始化保存
      └─ web: 登录注册入口、初始化向导、系统行为设置
```

建议新增一个独立策略包，而不是让业务代码继续直接读取全局变量：

```go
package policy

type UsageMode string

const (
    UsageModeExternal UsageMode = "external"
    UsageModePersonal  UsageMode = "personal"
    UsageModeDemo     UsageMode = "demo"
)

type RuntimePolicy struct {
    Mode                    UsageMode
    AllowRegistration       bool
    AllowPublicPricing      bool
    EnablePayment           bool
    EnableSubscriptions     bool
    EnableOAuthRegistration bool
    EnableMultiUserAdmin    bool
    RequireModelPricing     bool
    EnableTaskPlugins       bool
    EnableDeployments       bool
}
```

第一阶段不要求立刻替换所有读取点，但应该先增加：

```go
func IsPersonalUse() bool
func CurrentUsageMode() UsageMode
func IsFeatureEnabled(feature Feature) bool
```

后续所有功能裁剪都通过策略判断，避免在各个 Controller/React 页面散落 `if SelfUseModeEnabled`。

### 4.2 计费与协议转换的耦合

当前 Relay 请求生命周期大致是：

```text
TokenAuth
  → Distribute
  → 读取/校验请求
  → 选择渠道
  → 估算 Token
  → ModelPriceHelper
  → PreConsumeBilling
  → 上游协议转换
  → 上游请求/流式响应
  → Usage 解析
  → Settle / Refund
  → 写 Log
```

入口主要在：

- `middleware/auth.go`
- `middleware/distributor.go`
- `controller/relay.go`
- `relay/helper/price.go`
- `service/billing_session.go`
- `service/quota.go`
- `relay/` 和 `relaykit/`

个人模式不能简单删除计费模块，因为当前计费模块还承担：

- 请求前的额度保护；
- Token 额度扣减；
- 上游失败后的退款；
- Usage 统计；
- 任务和流式请求的结算；
- 模型列表是否可见的价格判断。

当前已落地的第一版终态记账窄接口为：

```go
type UsageAccounting interface {
    GetPreConsumedQuota() int
    Settle(actualQuota int) error
    Refund(c *gin.Context)
}

// 完整会话额外保留 NeedsRefund 和 Reserve。
```

它只承接已完成预扣会话的实际额度结算和异常退款；预扣策略、追加预留和运行模式选择暂时仍由现有服务层负责。此前规划的 `BeforeRequest + 原始 Usage` 接口作为远期策略层方向保留，等成本估算和记账边界进一步稳定后再实现。

然后再提供至少两个实现：

```text
PlatformAccounting   多用户/余额/订阅/分组/支付兼容
PersonalAccounting   单管理员/单资金来源/保留额度保护和用量记录
```

在第一阶段，`PersonalAccounting` 可以复用现有 `BillingSession` 的底层安全逻辑，但不再依赖订阅、用户分组和支付状态。

### 4.3 用户、Token、分组与渠道选择的耦合

当前关系：

```text
User
 ├─ Group
 ├─ Quota
 ├─ OAuth / Email / 2FA / Passkey
 ├─ TopUp / Subscription / Affiliation
 └─ Token[]
       ├─ Group / AutoGroups
       ├─ RemainQuota
       ├─ ModelLimits
       └─ CrossGroupRetry

Group + Model + Channel
 └─ Ability
      └─ 渠道优先级、权重、过滤和路由
```

个人模式的目标不是马上删除 User，而是把它收敛为：

```text
管理员 User
  └─ 多个 ClientToken
        ├─ 可选模型白名单
        ├─ 可选渠道/路由组
        └─ 可选请求审计标签
```

建议新增一个明确的路由上下文，不再让用户组直接承担渠道路由语义：

```go
type RoutingContext struct {
    RouteGroup       string
    Model            string
    RetryPolicy      RetryPolicy
    ChannelAffinity  string
}
```

迁移期间：

- `RouteGroup` 默认从 Token 的 Group/AutoGroups 兼容读取；
- 个人模式默认固定为 `default`；
- 渠道 `Ability` 继续工作；
- 等协议转换稳定后，再拆除用户计费组和渠道路由组之间的隐式关系。

### 4.4 前端导航与后端路由的耦合

前端目前存在三套入口控制：

1. React route 的 `beforeLoad` 权限判断；
2. `SidebarModulesAdmin` / `HeaderNavModules` 导航配置；
3. 后端 Gin 路由和 Controller 鉴权。

只改侧边栏是不够的。建议新增 `/api/status` 或 `/api/capabilities` 中的功能能力清单：

```json
{
  "usage_mode": "personal",
  "features": {
    "core_relay": true,
    "channel_management": true,
    "model_management": true,
    "token_management": true,
    "request_logs": true,
    "registration": false,
    "email_verification": false,
    "password_reset": false,
    "oauth": false,
    "user_management": false,
    "wallet": false,
    "payments": false,
    "subscriptions": false,
    "redemptions": false,
    "checkin": false,
    "pricing_portal": false,
    "rankings": false,
    "task_plugins": false,
    "deployments": false,
    "multi_node": false
  }
}
```

前端统一使用 `useFeatureAccess()`（路由守卫使用 `getFreshFeatureAccess()`）：

- 侧边栏不显示禁用模块；
- 路由 `beforeLoad` 拒绝直接访问；
- 页面不加载无用 API；
- 设置页不注册无用 section；
- 初始化向导只展示个人模式。

后端统一使用 `middleware.RequireFeature(feature)`：

- 未启用功能直接返回 404/403；
- Webhook、支付回调、注册 API 也必须受策略控制；
- 不能只依赖前端隐藏。

## 5. 推荐执行顺序

### 阶段 0：冻结基线和建立清单

目标：先保证后续删减可回滚、可定位。

工作：

1. 固定当前基线 commit 和 Go/前端版本。
2. 记录 `SelfUseModeEnabled=true` 时的现有行为。
3. 用 SQLite 完成初始化、管理员登录、创建 Token、创建渠道、模型列表和一次请求回归。
4. 导出当前路由表、数据库迁移模型清单、前端路由清单。
5. 建立“功能 → 路由 → Controller → Service → Model → 前端 → 迁移/依赖”的表格。
6. 为协议转换主线建立独立回归入口，避免精简工作掩盖协议 Bug。

验收：

- `go test ./...` 在当前基线通过或已有失败被记录；
- `cd web && bun run typecheck` 和 `bun run build` 结果被记录；
- 能明确区分“个人模式已有行为”和“计划新增行为”。

### 阶段 1：把个人模式从一个布尔开关升级为策略层

目标：让裁剪规则集中管理。

工作：

1. 在 `setting` 或新的 `policy` 包中定义 `UsageMode`、`Feature` 和 `RuntimePolicy`。
2. 保留数据库键 `SelfUseModeEnabled` 以兼容现有数据。
3. 将旧布尔值映射到 `UsageModePersonal`。
4. 新增 `GET /api/capabilities`，或扩展 `/api/status` 返回能力清单。
5. 增加后端 `RequireFeature` 中间件。
6. 增加前端 `useFeatureAccess()` 和统一路由保护。
7. 将初始化向导的 Personal use 选项作为默认的策略来源。

这一阶段不删除业务模块，只建立开关和契约。

### 阶段 2：先做 UI 精简，不动核心数据模型

目标：让个人模式先变得“看起来简单”，降低误操作风险。

个人模式默认导航只保留：

```text
概览（可选）
渠道
模型/路由
API Keys
使用日志
协议诊断/系统状态
个人设置
```

默认隐藏：

```text
钱包
充值
订阅
兑换码
用户管理
排行榜
价格展示页
任务插件
系统部署
运营型内容
```

系统设置只保留：

```text
渠道与协议
  - 渠道
  - 模型映射
  - 路由可靠性
  - OpenAI/Claude/Gemini 转换设置
令牌
  - API Key
  - 模型限制
日志与诊断
  - 请求日志
  - 协议转换诊断
基础安全
  - 登录
  - 2FA/Passkey（可选）
系统
  - 系统名称
  - 日志保留
  - 性能基础设置
```

实现重点：

- 不要通过写死 `SidebarModulesAdmin` JSON 来模拟精简；
- 导航配置应由能力清单和默认模式共同生成；
- 被隐藏的页面仍需要后端 Feature Guard；
- 前端删除或停用无用导入，避免打包进个人版资源。

### 阶段 3：关闭个人模式下的运营功能

目标：默认关闭并隔离所有“面向他人提供服务”的功能。

优先顺序：

1. 注册和邮箱验证；
2. OAuth 注册和 OAuth 绑定；
3. 找回密码邮件；
4. 支付 Webhook 和充值接口；
5. 订阅购买和订阅管理；
6. 兑换码；
7. 邀请/分成；
8. Check-in；
9. 公开价格、排行榜和运营首页内容；
10. 普通用户管理。

后端处理方式：

- 路由注册处按 Feature 分组；
- 个人模式下不注册不必要的路由，或在统一 Guard 中返回 404；
- Webhook 必须同样受策略限制；
- 初始化/迁移阶段不再创建新业务数据，但不要立刻删除已有表；
- 旧数据存在时，个人模式仍可启动并读取核心表。

前端处理方式：

- 在 route registry 中过滤；
- 在导航构建之前过滤；
- 不再加载对应 feature 的 API hooks 和页面；
- 删除无用的设置 section 注册。

### 阶段 4：拆出个人版计费与用量记账

目标：保留安全扣费和诊断，不再让个人主线依赖平台运营计费。

推荐拆分：

```text
relay/accounting/
├── interface.go
├── personal.go
├── platform.go
└── usage.go
```

`PersonalAccounting` 至少保留：

- 请求前限额/并发保护；
- Token 额度扣减或管理员级总额度；
- 上游失败退款；
- 实际 Usage 记录；
- 协议转换错误与渠道信息关联；
- 流式请求结束、异常断开和客户端取消的处理。

个人模式默认可以采用：

```text
管理员 User + 一个或多个 ClientToken
  → 统一 default 路由组
  → 单一 Wallet/Token 额度策略
  → 不启用订阅资金来源
  → 不启用支付充值
```

不要在这一阶段删掉 `BillingSession`，而是先把它依赖的 `FundingSource` 收敛到 `WalletFunding` 或新增 `PersonalFunding`，并为协议转换回归保留结算接口。

### 阶段 5：物理拆分非主线模块

只有在阶段 0-4 稳定后才进行。

推荐拆分成可选模块，而不是一开始做多个仓库：

```text
core
├── auth
├── channel
├── routing
├── relay
├── relaykit
├── accounting
└── diagnostics

optional
├── payments
├── subscriptions
├── oauth
├── task-plugins
├── image-video-tasks

```

Go 代码可以先通过目录和接口拆分，保持一个主模块；等依赖边界稳定，再考虑 Go build tags 或独立 module。前端可以用 feature entry 和 Rsbuild 分包，避免个人版把支付、订阅、任务等页面打进主 bundle。

## 6. 各模块的具体处理建议

### 6.1 认证与用户

**个人模式保留：**

- 管理员密码登录；
- Session/JWT/PAT 中用于后台和 API 的必要部分；
- Token 创建、撤销和模型限制；
- 2FA/Passkey（按需）；
- 管理员自身资料。

**默认关闭：**

- 注册；
- OAuth 注册；
- 邮箱验证；
- 找回密码邮件；
- 多普通用户管理；
- 用户邀请和绑定推广关系。

**解耦方案：**

- 保留 `model.User` 作为管理员账户载体，避免立即改表；
- 新增 `policy.IsRegistrationAllowed()`，而不是在 `controller.Register` 里直接读取全局变量；
- `userRoute.POST("/register")` 加 `RequireFeature(FeatureRegistration)`；
- 前端路由和登录页同时读取 capabilities；
- OAuth Provider 注册通过显式注册函数或 build option 注入，不让个人模式无条件 import 全部实现。

### 6.2 Token、额度与计费

**个人模式保留：**

- API Token；
- Token 模型白名单；
- 过期时间和撤销；
- 必要的额度/并发保护；
- 用量日志。

**默认关闭或隐藏：**

- Token 销售、充值、套餐和分组运营；
- 普通用户额度分配；
- 订阅资金来源；
- 充值/兑换/邀请带来的额度变化。

**解耦方案：**

- 将 `FundingSource` 作为计费抽象保留；
- 个人模式只注册 `PersonalFunding`；
- 平台模式再注册 Wallet/Subscription/Payment funding；
- `ModelPriceHelper` 拆分“上游成本估算”和“对外售价/分组倍率”；
- 个人模式使用成本统计或可选固定额度，不要求模型配置销售价；
- 不要删除 quota math、pre-consume、settle、refund，它们仍然是可靠性保护。

### 6.3 渠道与路由

这是个人版的主线，不应被运营模块拖累。

**保留：**

- Channel；
- Ability；
- 模型映射；
- 优先级/权重；
- 自动禁用和恢复；
- 渠道测试；
- 失败重试；
- 渠道亲和性缓存；
- 多 Key 渠道；
- 上游模型同步。

**第一阶段不要删除：**

- Group 字段；
- AutoGroups；
- CrossGroupRetry；
- ChannelInfo；
- Channel constraints。

原因是它们同时参与渠道选择、模型列表和失败重试。先把个人模式默认组固定为 `default`，再清理多组概念。

**后续解耦：**

```text
ChannelRoutePolicy
  ├── enabled
  ├── priority
  ├── weight
  ├── retryable
  ├── model_alias
  └── affinity
```

让路由策略从 User Group/价格 Group 中独立出来。

### 6.4 协议转换

这是 ModelPort 的核心改造区，建议完全独立于个人模式裁剪。

转换层需要保持：

```text
客户端协议
  → 解析
  → 统一 IR
  → 上游协议编码
  → 上游事件解析
  → 统一 StreamEvent
  → 下游协议编码
```

个人模式精简时不得删除：

- OpenAI Chat；
- OpenAI Responses；
- Anthropic Messages；
- Gemini；
- Tool Call；
- thinking/reasoning；
- 多模态；
- SSE；
- Usage；
- 错误和终止状态；
- 请求转换链路记录。

建议所有新转换代码放在 `relaykit/relayconvert` 或与之相邻的独立包，确保：

- 不依赖 User、Payment、Subscription；
- 不依赖 Gin；
- 不依赖数据库；
- 可独立单元测试；
- 个人版和平台版共享同一转换核心。

### 6.5 日志与诊断

个人版虽然没有多用户运营，也不能删除日志。建议把日志分成两层：

```text
RequestLog
  ├── request/response metadata
  ├── model/channel
  ├── latency/status
  ├── usage
  └── conversion diagnostics

PlatformAuditLog（可选）
  ├── user management
  ├── payment
  ├── subscription
  ├── role/permission
  └── administrative changes
```

个人模式默认只保留 `RequestLog` 和渠道配置变更审计。协议转换诊断建议记录：

- 客户端 RelayFormat；
- 最终上游 RelayFormat；
- RequestConversionChain；
- 是否发生 thinking/tool/image 降级；
- 上游 HTTP 状态和错误类型；
- stream 是否正常终止；
- usage 是否来自上游或估算；
- 重试次数和最终渠道。

敏感请求体和 API Key 仍然不能写入普通日志。

### 6.6 数据库和迁移

个人模式短期推荐：

- 默认 SQLite；
- 保留现有数据库兼容代码，避免无谓改动；
- 不因个人模式马上删除表；
- 新安装可以不创建可选业务表，但升级旧数据库必须兼容已有表；
- 如果改变 `AutoMigrate` 模型集合，必须在 SQLite、MySQL、PostgreSQL 上验证。

按照项目约束，任何数据库结构调整都必须：

- 在真实 SQLite、MySQL、PostgreSQL 实例上验证；
- 覆盖新库和旧版本升级库；
- 至少运行两次迁移确认幂等；
- 记录准确数据库版本、命令和结果。

如果只是第一阶段隐藏 UI 和增加策略，不涉及数据库结构，可以避免三数据库迁移成本。

## 10. 风险与禁止事项

### 不要做的事情

1. 不要把 `SelfUseModeEnabled` 直接扩展成各处散落的 `if` 判断。
2. 不要只删除前端菜单而不保护后端接口。
3. 不要一开始删除 User、Token、Quota、Ability、Option 等核心表。
4. 不要因为个人模式不收款就删除额度保护和退款逻辑。
5. 不要把 LiteLLM、New API 的协议转换代码和运营平台代码混在一起。
6. 不要先改数据库迁移，再去确认运行时依赖。
7. 不要在没有回归测试的情况下替换流式转换器。
8. 不要物理删除受许可证、上游归属或项目治理规则保护的信息。

### 主要风险

- 关闭计费后误删请求前额度保护；
- 删除 User 字段导致旧数据库 AutoMigrate 破坏；
- 删除 OAuth/邮箱代码时影响登录初始化；
- 删除 Task/Media 时破坏统一日志或插件路由；
- 个人模式与旧数据库数据不兼容；
- 前端 route、导航和后端 API 能力状态不一致；
- 个人模式下未配置价格导致模型列表和请求行为不一致；
- 删除重试/渠道状态逻辑，反而降低聚合网关可靠性；
- 协议转换包不小心依赖平台计费或 Gin，失去独立测试能力。

## 11. 最终验收标准

个人模式初步精简完成后，至少应满足：

1. 首次安装选择 Personal use 后，不能注册第二个用户。
2. 管理员可以创建和管理 API Token。
3. 管理员可以添加多个上游渠道和同一模型的多个渠道。
4. 渠道优先级、权重、失败重试正常工作。
5. OpenAI Chat/Responses、Anthropic Messages、Gemini 的核心转换回归通过。
6. 流式文本、思考内容、Tool Call、Tool Result、Usage 和错误终态回归通过。
7. 上游失败、客户端取消、连接中断时不会错误扣费或泄漏额度。
8. 个人模式不显示支付、订阅、兑换码、邀请、普通用户等平台功能。
9. 直接访问被禁用的接口会得到稳定的 404/403，不会执行副作用。
10. 协议转换核心不依赖支付、订阅、OAuth、任务部署等可选模块。
11. SQLite 个人部署可用；涉及迁移的变更经过三数据库验证。
12. 工作区、构建、测试和 Git 提交记录清晰，可随时回滚到精简前版本。

## 12. 结论

当前 `SelfUseModeEnabled` 只完成了“隐藏注册入口”和“放宽未配置模型价格”两个局部行为，不能直接作为精简依据。真正的初步精简应分成两条并行主线：

```text
主线一：个人模式策略化
  能力矩阵 → 后端 Guard → 前端导航/路由 → 运营模块默认关闭

主线二：协议转换核心化
  Relay/RelayKit 独立 → 统一 IR → 流式状态机 → 与用户/计费/支付解耦
```

第一阶段推荐只做策略层、UI 隐藏和后端 Guard，不删除核心表和核心业务；第二阶段再拆出个人记账和协议转换核心；最后才物理删除或模块化支付、订阅、OAuth、任务部署和多节点等可选功能。
