# 个人模式计费与用量记账解耦设计

> 文档日期：2026-09-02
> 最近更新：2026-09-02
>
> 本文说明个人版在移除平台运营模块后，如何按模型价格记录请求和任务用量，并处理异常终态。个人版不设置用户钱包余额，也不会因钱包余额不足拒绝请求。本文不修改协议转换器实现和 `relaykit` 公共 API。

## 1. 设计目标

个人版不提供支付、充值、订阅、兑换码、签到或邀请奖励。请求仍按模型价格计算并写入用量日志、用户累计用量和渠道统计；Token 的启用、过期、分组、模型和 IP 访问控制继续有效。

必须保留：

- 请求前额度估算和预扣；
- Token 额度预扣、补扣、差额退回和退款；
- 实际 Usage 结算；
- 上游错误、协议处理错误、取消、超时和扫描器异常的终态处理；
- 任务提交和任务轮询的计费；
- 日志、性能数据、quota saturation 审计和请求关联信息。

核心原则：

```text
删除支付入口 ≠ 删除费用记录
删除订阅来源 ≠ 删除请求记账生命周期
无最终 Usage ≠ 重复触发退款
异常终态只能完成一次结算或退款
```

## 2. 当前个人版链路

### 2.1 普通同步/流式请求

```text
Relay 请求入口
  → 请求解析和校验
  → 选择渠道、模型和重试策略
  → 估算预扣额度
  → PreConsumeBilling
  → NewBillingSession
  → 创建只记账的 BillingSession
  → 调用上游并执行协议转换
  → Handler 返回 Usage 或错误
  → 计算实际额度
  → SettleBilling 或 Refund
  → 写入用量、错误和诊断日志
```

### 2.2 异步任务

任务链路继续保留：

```text
任务请求
  → 估算任务额度
  → 创建只记账的 BillingSession
  → 提交上游任务
  → 保存 Task/TaskPlugin/Midjourney 状态
  → SystemTask 轮询
  → 任务成功按实际用量结算
  → 任务失败、超时或无法获得 Usage 时按任务既有语义退款
```

任务的 `ForcePreConsume` 不应被普通请求的信任额度旁路影响。

## 3. 当前实现边界

### 3.1 资金来源

当前 `FundingSource` 保留只记账的资金来源：

```go
type FundingSource interface {
    Source() string
    PreConsume(amount int) error
    Settle(delta int) error
    Refund() error
}
```

当前实现：

```text
UsageFunding
  → 不预扣用户余额
  → 不修改用户余额
  → 不执行余额退款
```

`BillingSession` 不再查询、预扣或结算订阅或钱包额度。`BillingSource` 当前标记为 `usage`。历史钱包和订阅字段只为数据库兼容保留，不参与运行时请求。

### 3.2 `BillingSession` 状态

`BillingSession` 保留以下状态：

```text
relayInfo
funding
preConsumedQuota
tokenConsumed
extraReserved
trusted
fundingSettled
settled
refunded
```

语义：

- `preConsumedQuota`：本次会话实际预扣的额度；
- `tokenConsumed`：已经从 Token 额度扣除的数量；
- `extraReserved`：切换渠道或重新估算时追加预扣的数量；
- `trusted`：命中可信额度旁路时，预扣额度可能为零；
- `fundingSettled`：钱包差额已成功提交，防止后续退款误退；
- `settled`：结算入口已经完成，重复结算直接返回；
- `refunded`：退款入口已经触发，重复退款直接返回。

这些状态和互斥保护是终态安全的一部分，不能因为个人版不收款而删除。

### 3.3 终态入口

普通请求通过 `relay/common/billing.go` 中的窄接口完成终态处理：

```go
type UsageAccounting interface {
    GetPreConsumedQuota() int
    Settle(actualQuota int) error
    Refund(c *gin.Context)
}

type BillingSettler interface {
    UsageAccounting
    NeedsRefund() bool
    Reserve(targetQuota int) error
}
```

`UsageAccounting` 只承接普通请求终态需要的读取预扣额度、实际额度结算和异常退款；`Reserve` 保留给渠道切换、阶梯计费和异步任务提交。

## 4. 结算和退款不变量

### 4.1 成功结算

```text
Handler 返回 Usage 且 error=nil
  → 计算 actualQuota
  → SettleBilling(actualQuota)
  → 只允许一次资金和 Token 差额调整
```

- 实际额度大于预扣：补扣差额；
- 实际额度等于预扣：不调整；
- 实际额度小于预扣：退回差额；
- 重复调用 `Settle`：额度不再变化。

### 4.2 异常退款

```text
Handler 返回 error
  → 外层失败清理
  → BillingSession.Refund 一次
```

退款入口必须同时保护钱包和 Token 额度：

- 钱包退款不是可无限重试的 `quota += N`；
- Token 退款不能在同一会话重复执行；
- 用量记账会话完成后，不能重复写入同一终态；
- 并发触发多个退款入口时只能有一个入口真正执行。

### 4.3 渠道重试

```text
第一个渠道失败
  → 保留本次会话和预扣状态
  → 切换下一个渠道
  → 最终成功：只按最终 Usage 结算一次
  → 全部失败：整个请求只退款一次
```

不能在每次渠道失败时立即退款，否则后续重试成功会造成额度回退和再次扣费不一致。

## 5. 流式、取消和无 Usage 的实际行为

当前终态以 Handler 返回的 `(Usage, error)` 为准，不单独根据流状态字段推断整笔退款。

| 场景 | 当前行为 | 记账结果 |
| --- | --- | --- |
| 流式正常结束并有 Usage | Handler 返回 Usage | 结算一次 |
| 截断流但已解析出部分 Usage | Handler 返回部分 Usage | 按部分 Usage 结算一次 |
| 客户端取消但 Handler 返回部分 Usage | 以返回 Usage 为准 | 结算一次，不强制整笔退款 |
| 上游错误且没有可用 Usage | Handler 返回 error | 退款一次 |
| 超时且没有可用 Usage | Handler 返回零 Usage 或 error | 按现有 Handler 终态执行一次结算或退款，不重复执行 |
| 扫描器/响应读取失败 | Handler 返回 error 或已有部分 Usage | 按返回值执行一次结算或退款 |
| 非流式响应无 Usage | 当前业务语义为零额度 | 结算为零，不额外再次调用退款 |
| 总 Token 为零 | 沿用 Handler 和当前业务语义 | 不产生负收费或重复退款 |

这一区分很重要：

- “没有 Usage”不自动等同于“调用退款入口”；
- 只有错误终态才走错误清理退款；
- 返回零 Usage 且无错误时，走一次零额度结算；
- 已完成的用量记账不能被后续异常清理重复处理。

## 6. 额度安全

个人版仍然遵循 `common/quota_math.go` 和 `pkg/billingexpr/expr.md` 的规则：

- 用户可控的数量、时长、批次、分辨率和质量倍率必须先限制上限；
- 预估和实际额度不能因整数溢出、NaN 或 Inf 变成负收费；
- quota clamp 必须写入 `relayInfo.QuotaClamp` 并进入管理员可见的日志审计；
- 预扣失败时不能静默溢出或进入负额度；
- Token 额度不足时应在用户钱包发生不可逆扣减前失败或回滚；
- 任何差额结算都必须使用集中式额度转换函数。

## 7. 已完成的回归覆盖

已经覆盖：

- 个人模式固定使用只记账的 `UsageFunding`；
- 历史订阅配置不会使个人请求进入订阅路径；
- 预扣额度大于、等于、小于实际用量时的三种结算；
- 上游错误退款一次；
- 响应读取/协议处理失败退款一次；
- 重复调用结算和退款入口不重复写入费用记录；
- 第一个渠道失败、第二个渠道成功只结算最终结果；
- 所有渠道失败只退款一次；
- 流式正常结束、截断流、客户端取消、超时和零 Usage；
- 任务提交和任务轮询的固定钱包计费；
- 任务计费测试夹具使用真实 SQLite 用户和 Token 数据。

## 8. 后续解耦顺序

当前不立即抽取第二套记账实现，顺序保持为：

```text
现有 BillingSession
  → 稳定 UsageAccounting 窄接口
  → 明确普通请求与异步任务的终态协议
  → 拆分个人模式记账策略
  → 评估剩余平台模块的可选化
```

后续可以把成本估算、预扣、结算、退款和日志拆成独立领域组件，但不能让协议转换器反向依赖支付、订阅或前端模块。

## 9. 路由分组与模型价格

个人版不再把分组作为账户等级或用户权限配置。计费和路由仍使用同一组配置，但只保留路由职责：

- `GroupRatio` 是路由分组的基础倍率；
- `GroupGroupRatio` 是 root 默认分组到目标路由分组的差异化计费倍率；
- `AutoGroups` 和 Token 自动分组控制自动路由顺序；
- Token 指定的分组继续限制本次请求的候选渠道；
- root 管理员默认可以使用所有已配置路由分组，旧 `UserUsableGroups` 和 `GroupSpecialUsableGroup` 不再参与运行时判断；
- `/api/pricing` 继续提供模型广场需要的模型价格、厂商、接口类型、分组倍率和自动分组数据；
- 模型价格展示与实际计费共用模型价格和分组倍率配置，但不恢复任何充值、订阅或公开商业售卖功能。

删除账户用户组不会删除历史日志中的 `user_id`、`username` 或 `group` 字段；这些字段仍用于审计、兼容和账单追踪，不再用于用户等级、权限分流或运营排行。

## 10. 当前禁止修改

- 不修改 `relay/`、`relaykit/` 的转换器实现和公共转换 API；
- 不为测试修改真实协议语义；
- 不删除 `BillingSession`、`UsageAccounting`、`FundingSource`、费用记录或异常终态逻辑；
- 不恢复支付、订阅、充值、兑换码和邀请入口；
- 不删除任务计费、任务轮询、节点协调和系统任务能力；
- 不修改数据库 Schema 之外的核心数据模型，除非后续阶段单独批准。
