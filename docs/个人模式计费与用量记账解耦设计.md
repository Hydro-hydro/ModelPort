# 个人模式计费与用量记账解耦设计

> 文档日期：2026-09-02
> 最近更新：2026-09-02
>
> 本文只设计个人模式的计费与用量记账边界，暂不修改协议转换核心、数据库结构和现有计费安全逻辑。

## 1. 设计目标

ModelPort 的个人模式主要用于聚合多个上游 AI 渠道，并向个人客户端提供统一 API。个人模式不需要支付、充值、订阅和多用户运营功能，但仍然需要完整的内部用量记账能力。

本阶段目标：

- 保留请求前预扣费，防止无限制请求和额度竞争；
- 保留请求完成后的实际用量结算；
- 保留上游失败、客户端中断和异常路径的退款能力；
- 保留 Token 额度限制、并发安全、用量统计和日志审计；
- 个人模式默认使用管理员用户额度作为内部资金来源；
- 不让个人模式依赖支付状态、充值订单、订阅套餐或兑换码；
- 不改变 `relay/`、`relaykit/` 中的协议转换行为。

核心原则：

```text
关闭对外售卖功能 ≠ 删除内部额度保护
删除平台资金来源 ≠ 删除请求记账生命周期
个人模式简化 ≠ 把请求变成无保护的免费转发
```

## 2. 当前实现盘点

### 2.1 计费表达式

计费表达式系统的设计约束见：

```text
pkg/billingexpr/expr.md
```

当前表达式系统负责：

- 用一个表达式描述模型价格、缓存、图片、音频和阶梯规则；
- 根据 AST 判断表达式实际使用的变量；
- 规范化 OpenAI/GPT 与 Claude 的 Token 统计差异；
- 计算预估额度和实际额度；
- 生成带版本信息的计费快照；
- 将计费表达式和阶梯命中信息写入日志。

个人模式不能绕过这些逻辑。即使不向用户收费，也需要使用同一套模型成本估算和用量统计，以便：

- 判断请求是否应该允许发送；
- 保护管理员额度和 Token 额度；
- 统计不同渠道和模型的实际使用量；
- 定位协议转换、Usage 解析和上游扣费异常。

### 2.2 当前请求记账链路

当前主要链路如下：

```text
Relay 请求入口
  → 解析和校验请求
  → 选择渠道与模型
  → 估算模型额度
  → PreConsumeBilling
  → NewBillingSession
  → Token 额度预扣
  → FundingSource 资金来源预扣
  → 调用上游并执行协议转换
  → 读取上游 Usage
  → 计算实际额度
  → SettleBilling
  → 资金来源差额结算
  → Token 额度差额结算
  → 写入用量/错误/计费日志
```

关键实现位置：

| 环节 | 文件 | 当前职责 |
| --- | --- | --- |
| 统一预扣和结算入口 | `service/billing.go` | 创建会话、预扣、结算和旧逻辑兼容 |
| 计费会话 | `service/billing_session.go` | 管理预扣、补充预扣、结算、退款和幂等状态 |
| 资金来源 | `service/funding_source.go` | 实现钱包和订阅两类资金来源 |
| 用户/Token 额度 | `service/quota.go` | 预扣、差额结算、退款和额度通知 |
| 模型成本估算 | `relay/helper/price.go` | 模型价格、表达式和预扣额度计算 |
| 表达式预估 | `relay/helper/billing_expr_request.go` | 根据请求信息生成表达式计费预估 |
| 表达式实际结算 | `service/tiered_settle.go` | 根据真实 Usage 重新计算实际额度 |
| 额度安全转换 | `common/quota_math.go` | 限制溢出、NaN、Inf 和边界转换 |
| 日志计费信息 | `service/log_info_generate.go` | 保存计费快照、Usage、规则轨迹和异常标记 |

### 2.3 当前 `BillingSession` 状态

`BillingSession` 当前同时管理：

```text
relayInfo
funding
preConsumedQuota
tokenConsumed
extraReserved
trusted
fundingSettled
settled
refunded
```

其中：

- `preConsumedQuota`：当前会话实际预扣的额度；
- `tokenConsumed`：Token 额度已经扣减的数量；
- `extraReserved`：发送请求前因切换更贵渠道/分组而追加预扣的数量；
- `trusted`：命中可信额度旁路时不做实际预扣；
- `fundingSettled`：资金来源已经完成差额结算，防止再次退款；
- `settled`：整个会话完成结算；
- `refunded`：退款流程已经触发，保证退款入口幂等。

这些状态是请求生命周期安全的一部分，不能因为个人模式不收款而删除。

### 2.4 当前资金来源

当前 `FundingSource` 接口为：

```go
type FundingSource interface {
    Source() string
    PreConsume(amount int) error
    Settle(delta int) error
    Refund() error
}
```

当前实现：

```text
WalletFunding
  → 用户额度预扣、结算、退款

SubscriptionFunding
  → 订阅额度预扣、结算、退款
```

`NewBillingSession` 会根据用户的 `BillingPreference` 和订阅状态在两类来源之间选择：

```text
subscription_only
wallet_only
wallet_first
subscription_first
```

这意味着在本轮改造前，个人模式虽然已经关闭了订阅相关入口，但底层会话仍然可能根据既有用户配置进入订阅路径。这是后续需要通过策略边界处理的耦合点。

本轮已经完成第一步策略边界：`NewBillingSession` 在 `usage_mode.IsPersonalUse()` 为真时直接选择 `WalletFunding`，不读取 `BillingPreference`，也不查询或预扣历史订阅；外部模式和演示模式继续使用原有的计费偏好选择逻辑。

## 3. 个人模式目标记账策略

### 3.1 第一阶段策略

第一阶段不新增独立的个人资金表，也不重写现有计费会话。本轮已经落地兼容策略：

```text
个人模式
  → NewBillingSession 直接选择 WalletFunding
  → 继续使用 BillingSession
  → 继续使用 Token 额度预扣/结算/退款
  → 不暴露支付、充值、订阅运营入口
  → 暂不删除 SubscriptionFunding
```

这里的 `WalletFunding` 代表管理员额度账户，并不代表个人模式开放了钱包充值页面。

### 3.2 个人模式必须满足的约束

| 约束 | 说明 |
| --- | --- |
| 请求前额度保护 | 预估额度过大或管理员额度不足时，不应发送请求 |
| Token 额度同步 | 非 Playground 请求必须同步扣减 Token 额度 |
| 失败退款 | 上游失败、协议错误和请求异常必须释放预扣额度 |
| 结算幂等 | 重复调用结算不能重复扣款或退款 |
| 退款幂等 | 重复触发失败处理不能重复增加额度 |
| 差额安全 | 实际额度大于预估时补扣，小于预估时退回差额 |
| 饱和安全 | quota clamp、NaN、Inf 和负数输入不能造成负收费 |
| 日志一致 | 预扣、实际 Usage、结算和异常信息可以关联到同一请求 |
| 协议无关 | 计费生命周期不能侵入协议转换器内部 |
| 运营解耦 | 不依赖支付订单、订阅购买或充值回调才能完成普通请求 |

### 3.3 暂不改变的内容

以下内容本阶段保持不变：

- `BillingSession` 的状态机和互斥保护；
- `FundingSource` 接口；
- `WalletFunding` 和 `SubscriptionFunding` 的现有实现；
- `PreConsumeBilling`、`SettleBilling` 和退款入口；
- `common/quota_math.go` 的边界转换与饱和审计；
- `BillingSnapshot`、表达式变量规范化和阶梯结算；
- Token 额度的原子预扣和回滚；
- `relay/`、`relaykit/` 和各提供商适配器。

## 4. 解耦方案

### 4.1 先建立记账边界，而不是马上移动目录

第一步只定义概念边界，不移动现有文件：

```text
请求计费生命周期
  ├─ CostEstimation     模型成本/额度估算
  ├─ Reservation        请求前预扣和追加预扣
  ├─ Settlement         实际 Usage 结算
  ├─ Refund             异常退款
  └─ UsageAudit         用量和异常日志
```

建议后续形成窄接口：

```go
type UsageAccounting interface {
    BeforeRequest(ctx context.Context, info *RelayInfo) error
    Settle(ctx context.Context, info *RelayInfo, usage Usage) error
    Refund(ctx context.Context, info *RelayInfo) error
}
```

但在接口真正落地前，必须先用现有 `BillingSession` 建立行为测试，避免把未理解的状态机错误地抽象掉。

### 4.2 个人记账实现的边界

未来的 `PersonalAccounting` 只负责个人模式的资金来源选择和请求记账策略，不负责：

- OpenAI/Claude/Gemini 请求转换；
- 流式事件解析；
- 渠道选择；
- 模型价格表达式解析；
- 支付订单和充值回调；
- 数据库迁移。

建议的依赖方向：

```text
relay/controller
  → UsageAccounting 接口

PersonalAccounting / PlatformAccounting
  → BillingSession / quota / usage log

BillingSession
  → FundingSource

FundingSource
  → model quota or subscription persistence
```

协议转换器只能输出请求结果、Usage 和错误终态，不应反向依赖支付、订阅或前端模块。

### 4.3 个人模式资金来源选择

未来个人模式可以在 `NewBillingSession` 外层增加策略选择：

```go
if usage_mode.IsPersonalUse() {
    return newPersonalBillingSession(...)
}
return newPlatformBillingSession(...)
```

第一版 `newPersonalBillingSession` 不需要新建数据库结构，可以：

1. 复用当前用户额度查询；
2. 固定选择 `WalletFunding`；
3. 保留 Token 额度预扣；
4. 保留 `BillingSession` 的结算和退款；
5. 明确不调用订阅查询和订阅预扣；
6. 通过单元/集成测试证明个人模式不会进入订阅路径。

该改动应在测试基线建立后再实施，不能现在直接改动计费工厂。

## 5. 回归测试计划

### 5.1 测试优先级

优先验证个人模式真正依赖的行为，避免重复覆盖已有平台计费测试：

#### P0：必须先覆盖

1. **个人模式普通请求成功**
   - 固定管理员用户和 Token；
   - 设置个人模式；
   - 使用钱包额度预扣；
   - 实际额度与预估一致时不产生重复调整；
   - 用户额度、Token 额度和日志结果一致。

2. **个人模式上游失败退款**
   - 预扣成功后模拟上游失败；
   - 触发退款；
   - 用户额度和 Token 额度完整恢复；
   - 重复触发退款不会重复返还。

3. **个人模式实际用量大于预估**
   - 预扣较小额度；
   - 结算更大实际额度；
   - 只补扣差额；
   - Token 额度和用户额度变化一致。

4. **个人模式实际用量小于预估**
   - 预扣较大额度；
   - 结算更小实际额度；
   - 只返还差额；
   - 不进入完整失败退款路径。

5. **个人模式禁止订阅资金来源**
   - 个人模式下即使存在旧的 `subscription_first` 配置；
   - 计费会话也不得查询或预扣订阅；
   - 请求继续使用管理员额度路径。

#### P1：随后覆盖

6. **个人模式 Token 额度不足**
   - 预扣失败；
   - 用户额度不发生提前扣减；
   - 返回额度不足错误。

7. **个人模式 quota clamp**
   - 使用会触发额度饱和的输入；
   - 请求在预扣前失败；
   - 不产生负额度；
   - 记录可审计的 clamp 信息。

8. **流式请求异常终态**
   - 模拟流式上游错误、客户端中断或没有最终 Usage；
   - 验证结算/退款只执行一次；
   - 不修改协议转换核心，只测试其向计费层输出的终态。

9. **个人模式无支付/无订阅运营依赖**
   - 禁用个人模式相关运营能力；
   - 普通请求不访问支付和订阅运营 Controller；
   - 既有历史订阅数据不影响核心转发启动。

### 5.2 测试夹具要求

新增测试应：

- 使用显式的用户、Token、额度、模型和请求上下文；
- 使用真实的 SQLite 测试数据库，除非测试仅验证纯状态机；
- 通过 `require` 完成初始化和致命断言；
- 通过 `assert` 完成值和非致命结果断言；
- 不使用随机输入、休眠、耗时比较或仅断言日志输出；
- 不为了测试而修改协议语义；
- 每个测试只验证一个真实的个人模式不变量。

### 5.3 普通 Relay 终态回归

新增 `/Users/hydro/Documents/ModelPort/controller/personal_relay_billing_test.go`，通过本地上游 HTTP 服务实际调用普通 Relay，验证外层 `Relay`、Handler 和 `BillingSession` 的连接方式：

- 上游 HTTP 错误和响应解析失败：Handler 返回错误，外层失败清理路径调用一次 `Refund`，用户额度和 Token 额度恢复；
- 首次渠道失败、重试成功：预扣额度在重试期间保持不变，只对最终 Handler 返回的 Usage 结算一次；
- 所有渠道失败：重试结束后统一退款一次，不在每次失败尝试中提前退款；
- 普通流式请求正常结束：最终 Usage 通过 `PostTextConsumeQuota` 进入一次 `SettleBilling`；
- 截断流没有 `[DONE]`：当前 OpenAI Handler 将可得到的响应内容转换为 Usage，仍按 Handler 返回的 Usage 结算，不额外触发退款；
- 客户端取消：流状态为 `client_gone` 时，当前 Handler 可能返回部分 Usage，记账层按该 Usage 结算；不能仅凭流状态强制执行完整退款；
- 流式超时且没有可用 Usage：当前 Handler 返回零 Usage，记账层按 `actualQuota=0` 结算并释放预扣额度；
- 非流式零 Usage：当前业务语义同样是按零额度结算，不重复调用退款。

因此，当前普通 Relay 的终态判断仍以 Handler 的 `(Usage, error)` 输出为准：

```text
Handler 返回 error
  → Relay 外层失败清理
  → BillingSession.Refund 一次

Handler 返回 Usage 且 error=nil
  → PostTextConsumeQuota
  → SettleBilling 一次
```

这些回归测试没有修改 `relay/`、`relaykit/` 或协议转换实现，只验证它们向计费层输出的终态。

9. 数据库 Schema 没有未经计划的变化；
