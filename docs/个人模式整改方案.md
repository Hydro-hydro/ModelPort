# 个人模式整改方案

> 文档日期：2026-09-05
> 文档性质：个人模式的唯一事实来源
>
> 本方案面向全新部署的 ModelPort。项目不负责旧 New API 数据迁移，不兼容旧数据库结构，也不通过启动清理旧表、旧字段或旧配置来完成升级。协议转换器和 `relaykit` 公共 API 不在本方案中修改。

## 1. 产品定位

ModelPort 是面向个人部署的 AI API 聚合网关与协议转换器：将多个上游渠道、模型和 API Token 收敛到一个统一入口，重点解决请求参数、流式响应、工具调用、思考内容、Usage 和错误信息的协议兼容问题。

个人模式的目标不是继续维护一个多用户运营平台，也不是把项目裁剪成只能转发单一模型的代理，而是形成一个单管理员、可配置、可诊断、可扩展的个人网关。

核心目标如下：

- 一个 root 管理员完成全部管理工作；
- 保留多渠道聚合、模型映射、路由选择、失败重试和统一 API 入口；
- 保留协议转换、流式处理、工具调用、媒体接口和用量诊断；
- 按模型价格记录实际使用费用，但不设置个人钱包余额；
- 使用 API Token 提供访问控制、模型限制、过期和可选额度上限；
- 将任务、部署和多节点作为可选能力，默认关闭；
- 用新库初始化降低部署复杂度，不为历史平台数据承担迁移责任。

## 2. 功能边界

### 2.1 核心能力：默认启用

以下能力直接服务于个人 API 网关主线，必须保留：

- root 管理员密码登录、Session/JWT 和基础安全校验；
- 渠道管理、上游 Key、Base URL、代理、模型列表和渠道测试；
- 渠道能力表、启用状态、优先级、权重、失败重试和亲和性缓存；
- 模型目录、模型映射、模型价格和按模型记录的使用费用；
- 路由分组、自动分组、Token 指定分组和分组配置页面；
- API Token 创建、撤销、过期、模型白名单、IP 限制和访问额度上限；
- OpenAI Chat Completions、OpenAI Responses、Anthropic Messages、Gemini 等协议的请求和响应转换；
- 流式响应、工具调用、思考内容、图片、音频、Embedding 和 Rerank 等已支持的同步中继能力；
- 请求日志、错误日志、用量统计、性能指标、渠道诊断和转换链路信息；
- 必要的缓存、限流、健康检查和运行状态。

### 2.2 可选能力：默认关闭

这些能力不属于个人网关的最小启动路径，但在确有需求时可以单独启用：

- 异步任务和任务插件；
- 视频、Suno、Midjourney 等媒体任务；
- io.net 部署和其他部署能力；
- 多节点、节点状态上报和节点协调；
- 高级认证能力，例如 2FA、Passkey 或第三方身份接入；
- 依赖后台轮询的任务产物代理和扩展任务适配器。

可选能力关闭时，应同时从默认导航、配置入口和能力接口中关闭；启用后必须拥有独立的后端权限校验、任务状态和计费测试。关闭可选能力不删除其代码和数据模型，避免影响核心网关的构建边界。

### 2.3 永不提供的平台运营能力

个人版不提供以下能力及其配置入口：

- 注册、多普通用户管理、组织和团队隔离；
- OAuth 注册、邮箱验证、密码找回和面向普通用户的认证流程；
- 钱包余额、充值、提现、支付渠道和支付回调；
- 订阅套餐、订阅购买、兑换码、签到、邀请、推广、分成和排行榜；
- 面向访客的商业价格页、销售价格和营销首页内容。

删除这些能力不能连带删除模型成本记录、Token 访问控制、路由分组、请求日志或协议诊断。

## 3. 全新部署和数据模型原则

### 3.1 只支持新库初始化

项目只保证当前版本在空数据库上的初始化和重复启动幂等：

- SQLite、MySQL 和 PostgreSQL 均从当前模型清单直接创建；
- 不读取、转换或清理旧 New API 表、字段、索引和配置；
- 不执行旧版本约束修复、类型升级、删除旧运营表或删除旧用户字段；
- 不为旧库增加兼容 fallback、迁移开关或历史数据恢复路径；
- 发现数据库不是当前版本的新库结构时，应明确报错并要求重新初始化，而不是猜测性修复。

新库 schema 只包含个人版当前需要的模型：渠道、能力、模型、Token、root 管理员、会话、请求日志、用量统计、任务相关可选模型、系统任务、节点相关可选模型、权限规则和账单操作记录。支付、订阅、充值、邀请、签到、排行榜和第三方用户运营表不进入新库模型清单。

### 3.2 钱包彻底退出

个人版不设置用户钱包余额，也不因余额不足拒绝请求。费用语义只有两类：

1. 模型价格产生的实际使用费用，用于用量日志、统计和诊断；
2. API Token 的访问额度上限，用于限制 Token 是否还能继续调用。

新部署不创建 `User.Quota` 之类的钱包余额字段，不保留余额预警、钱包充值或钱包资金来源。累计使用量如需展示，应使用明确的统计语义，不得再解释为可消费余额。

## 4. 个人模式计费与用量记账

### 4.1 计费原则

个人版按模型价格记录费用，不建立充值资金闭环：

```text
请求/任务
  → 校验请求与 Token 访问限额
  → 计算模型价格和预计用量
  → 预扣有限 Token 额度（如启用）
  → 调用上游或提交任务
  → 采集最终 Usage
  → 仅结算模型使用记录和 Token 实际差额
```

预扣、补扣和退款是访问额度保护，不是钱包扣款。有限 Token 额度必须使用带条件的原子更新，任何路径都不能产生负的剩余额度。

### 4.2 普通请求终态

- 入口只执行一次预扣；渠道重试沿用同一个记账会话；
- 第一个渠道失败、第二个渠道成功时，只按最终有效 Usage 结算一次；
- 实际用量大于预扣时补扣差额，小于预扣时退回差额，相等时不调整；
- 上游错误、协议处理错误、取消和超时没有有效 Usage 时执行一次退款；
- 无 Usage 但请求正常返回时，按当前模型计费语义记为零用量，不重复调用退款；
- 重复调用 `Settle` 或 `Refund` 必须幂等，进程重启后也不能再次调整 Token 额度。

### 4.3 Realtime 终态

- 连接入口只预扣一次；两个 WebSocket reader 只传递事件并汇总用量；
- 每个上游 `response.usage` 最多采纳一次；存在上游 Usage 时不再与本地估算相加；
- 连接关闭、取消或异常时，先停止并等待两个 reader，再读取最终快照；
- 多段 `response.done` 只形成一个最终记账结果；
- 结束时只执行一次 `Settle` 或 `Refund`，并统一使用最终 `PriceData.UsePrice`。

### 4.4 持久化账单操作

为跨进程恢复、异步任务和独立日志库场景保留主数据库账单操作表。该表只记录用量和 Token 额度操作，不包含钱包、充值或订阅资金来源。

至少包含：

- 唯一 `operation_key`、请求或任务标识；
- 用户、Token、渠道、预计额度和实际额度；
- Token、统计、日志等组件的完成标记；
- `reserved`、`applying`、`settled`、`refund_pending`、`refunded` 等状态；
- 尝试次数、下次重试时间、最后错误、worker 租约和更新时间。

执行顺序固定为“先落账单操作，再应用额度和统计变化”。每个组件使用 `operation_key + component` 幂等；后台 runner 使用 CAS、租约和退避重试。独立日志库不参与跨库事务，日志通过可重试的 outbox 事件投递。

账单状态只有在 Token 额度、统计和日志等必要组件全部成功后才能进入完成态。失败不得提前标记完成，退款失败不得提前标记 `refunded`，任务 `Quota` 只有在结算或退款全部完成后才能清零。

### 4.5 异步任务终态

任务能力默认关闭；启用后必须沿用同一套账单操作语义：

- 成功、失败、取消和超时统一通过带账单状态的 CAS 终态处理；
- 上游任务 ID 缺失且无法轮询时，标记任务失败并创建退款操作；
- 渠道缓存、适配器、HTTP 或解析临时失败时保留任务等待下一轮，不直接批量失败；
- 超过超时阈值后由统一超时处理器失败并退款；
- 涉及计费的状态转换禁止使用无 CAS 的批量更新；
- 重复轮询、进程重启和多节点竞争最多产生一次结算或退款。

## 5. 路由分组与分组配置

分组是网关路由配置，不是用户等级、组织权限或商业销售分组。前端必须提供完整的“分组配置”入口，不能因为删除钱包和运营设置而隐藏分组配置。

分组职责如下：

- `GroupRatio`：路由组的基础模型价格倍率；
- `GroupGroupRatio`：特定来源路由组到目标路由组的倍率覆盖；
- `AutoGroups`：自动路由时的分组尝试顺序；
- Token 分组：限制该 Token 本次请求可使用的路由组；
- 渠道 `Ability.Enabled`、渠道状态和模型能力：决定路由索引是否有效。

实现要求：

- root 管理员默认可以使用所有已配置路由组；
- 组名不再使用 VIP、SVIP 等账户等级语义，默认配置以 `default` 和实际渠道路由需求为准；
- 渠道启用时立即恢复 group/model 索引，禁用时同步移除；
- 数据库读取失败时不能用空结果覆盖已有缓存；
- `Channel` 与 `Ability` 的增删改必须在同一数据库事务中完成；
- 配置 JSON 先解析和验证到临时对象，成功后在写锁下替换，数据库写失败不能更新运行时配置；
- 模型价格、分组倍率、厂商列表和展示缓存统一加读写保护，变更后立即失效相关缓存。

## 6. 协议转换边界

协议转换是 ModelPort 的核心改造区，与个人模式裁剪解耦。本阶段不修改：

- `relay/` 下现有协议转换器的公共行为；
- `relaykit/` 的公共 API、DTO 和独立模块边界；
- 已有客户端协议与上游协议的转换语义。

后续协议专项工作必须先建立“客户端格式 × 上游渠道 × 流式/非流式 × Usage/错误终态”的回归矩阵，再针对最小复现用例进行修改。个人版精简不得通过删除协议能力来掩盖转换问题。

## 7. 整改顺序

### 阶段一：确定个人版运行边界

- 固定单一 root 管理员；
- 固定关闭注册、OAuth、邮箱、普通用户管理和全部平台运营能力；
- 任务、部署、多节点和高级认证纳入能力开关，默认关闭；
- 保留渠道、模型、Token、路由分组、日志和协议诊断入口。

### 阶段二：删除钱包和旧平台语义

- 从个人版运行时计费中删除钱包资金来源、余额预扣、余额结算和余额预警；
- 清理余额展示、余额通知、充值文案、钱包 DTO 和相关接口；
- 将累计用量、模型费用和 Token 访问额度使用清晰且互不混淆的命名；
- 删除只服务于旧平台迁移的代码、配置和测试，不添加新的旧库兼容分支。

### 阶段三：稳定核心计费链路

- 完成普通请求、Realtime 和 Token 额度的单次预扣、单次结算、单次退款；
- 落实账单操作表、组件幂等、CAS、租约和补偿 worker；
- 补齐上游多段 Usage、无 Usage、取消、异常关闭、超时、重试和重复终态测试；
- 费用统计、请求日志、渠道统计和 Token 最终额度必须与最终模型费用一致。

### 阶段四：稳定路由与配置

- 恢复并完善“分组配置”前端入口；
- 统一路由组、模型价格倍率和自动分组的语义；
- 修复能力索引、渠道启停、配置替换、缓存失效和并发读写一致性；
- 确认禁用能力不可路由，启用能力立即恢复。

### 阶段五：按需启用可选能力

- 只有确认有需求时才启用任务、媒体任务、部署或多节点；
- 每项可选能力必须独立验证权限、状态机、轮询、日志和计费；
- 默认关闭路径不应加载不必要的后台 worker、页面和运行时依赖。

### 阶段六：协议转换专项回归

- 在核心计费、路由和配置稳定后，建立协议转换回归矩阵；
- 逐项修复请求参数、流式事件、工具调用、思考内容、Usage 和错误映射；
- 保持 `relaykit` 可独立构建，不改变公共 API。

## 8. 验收标准

### 计费和额度

- 个人钱包不存在且不会被读取、扣减或用于拒绝请求；
- 模型费用只写入用量、统计和日志；
- Token 额度并发补扣不出现负数，预扣、结算和退款最多执行一次；
- 费用为零、Usage 缺失、上游错误、取消、超时和重复终态均有确定结果；
- Realtime 多段 `response.done`、上游 Usage 与本地估算互斥，关闭竞态不会重复记账。

### 路由和配置

- 禁用的渠道能力不能进入路由，重新启用后索引立即恢复；
- 分组配置页面可以读写基础倍率、跨组倍率、自动分组和 Token 分组限制；
- 非法 JSON 不清空旧配置，数据库写失败不污染运行时配置；
- 缓存刷新失败不会丢失可重试的数据，核心 map 并发读写无 race。

### 可选能力

- 任务、部署、多节点默认关闭时不出现在默认入口，也不会影响普通同步中继；
- 启用后任务终态、轮询、节点竞争和账单操作具备 CAS 与幂等保护。

### 新库验证

- SQLite、MySQL `>= 5.7.8`、PostgreSQL `>= 9.6` 分别验证全新数据库初始化；
- 至少连续启动/初始化两次，确认迁移幂等、索引和唯一性稳定；
- 不执行旧库升级测试，不把旧 New API 数据迁移列为验收目标；
- `relaykit` 使用 `cd relaykit && GOWORK=off go build ./...` 独立验证；
- 核心回归命令至少包括 `go test ./service ./model ./relay/channel/openai`，修复既有 race 后再运行 `go test -race`。

## 9. 明确禁止事项

- 不恢复钱包、充值、支付、订阅、兑换码、签到、邀请或普通用户运营；
- 不把路由分组重新解释为账户等级、组织权限或销售价格分组；
- 不因删除运营模块而删除模型价格、Token 访问控制、日志、任务计费接口或协议诊断；
- 不为旧 New API 数据添加迁移、清理、兼容 fallback 或历史字段保留方案；
- 不通过前端隐藏代替后端能力校验；
- 不修改项目名称、作者、版权、许可证和归属信息；
- 不修改 `relay/`、`relaykit/` 的转换器公共 API，除非后续协议专项明确批准。
